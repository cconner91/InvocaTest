Client-Side Lead Capture — SPA Simulation

Client-Side Form (SPA Multi-Step)

Each step below fully destroys and rebuilds its own DOM — including the <form> element itself — the same way a Next.js route change unmounts and remounts a page's component tree. Field values are held in JS state between steps, not in a persistent form.

Dev note: This page tests something the other two client-side pages can't. It rebuilds the form on every step transition via innerHTML replacement, so the final step's #sfLeadForm-spa element is a different DOM node than the one present on step 1 — deliberately mimicking a real SPA route change (e.g. this account's actual multi-step flow, which uses a Next.js catch-all route per step). The custom invocaLeadSubmit event is dispatched on that freshly-mounted final node, which tests whether InvocaJS's listener survives DOM churn or is bound to a now-detached element.
  • This form uses its own selector, leadFormSelector: "#sfLeadForm-spa" — separate from the native forms' shared #sfLeadForm — because it needs leadFormSubmitEvent: "invocaLeadSubmit" instead of the default submit. Whether one Tag's custom code can hold both configs at once is still an open question.
  • The hidden invoca_attribution_id field is re-rendered fresh on every step. Worth watching whether it's populated at the moment of final submit, or whether InvocaJS only ever populated the step-1 instance that no longer exists by then.
